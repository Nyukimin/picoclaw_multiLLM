# ログViewer 現行仕様サマリ 2026-03-19

**対象**: RenCrow Viewer / Chat / Worker / Coder 監視
**ステータス**: 現行実装ベース
**参照**: `docs/ログViewer仕様.md`, `docs/実装仕様_ログViewer_v1.md`, `docs/実装仕様_操作ログJSON保持_v1.md`

## 1. 目的

ログViewerは、RenCrow のユーザー向け会話、Chat / Worker / Coder の内部挙動、job 進行、evidence、IdleChat をブラウザから確認するための運用 Viewer である。

現行実装では、以下の 3 系統を分けて扱う。

- ライブ監視: `EventHub` + `/viewer/events`
- 後追い監査: `workspace/orchestrator_event_log.jsonl`
- 運用 UI: `/viewer`

## 2. 監視対象

固定の役割分類:

- Chat: `mio`
- Worker: `shiro`
- Coder: `coder1`, `coder2`, `coder3`

主な追跡単位:

- `job_id`
- `route`
- `session_id`
- `chat_id`
- `from`
- `to`

## 3. 画面構成

現行 `viewer.html` は以下の 8 タブを持つ。

- `Ops`
- `Overview`
- `Progress`
- `Timeline`
- `System`
- `IdleChat`
- `Sessions`
- `Jobs`

各タブの役割:

- `Ops`: 運用者向け要約。最新 job、Mio 最終報告、進行中 job、直近 error、稼働 agent、主要イベントをまとめて見る
- `Overview`: `mio / shiro / coder1-3` の現在状態を俯瞰する
- `Progress`: job ごとの段階、担当、最新の chat/worker/coder note、失敗理由を確認する
- `Timeline`: ユーザー向けの流れを時系列で見る。最終報告の正本は Mio
- `System`: routing、handoff、mailbox、error などの技術イベントを追う
- `IdleChat`: IdleChat の状態、ログ、制御
- `Sessions`: session 単位の集約
- `Jobs`: job 一覧、詳細、evidence 参照

## 4. Progress の現行段階

`Progress` は Chat だけでなく Worker / Coder まで追える。

主な phase:

- `received`
- `routing`
- `delegating`
- `chatting`
- `to worker`
- `to coder`
- `queued`
- `waiting`
- `processing`
- `verifying`
- `retrying`
- `reporting`
- `done`
- `error`

phase への主な対応:

- `message.received` -> `received`
- `routing.decision` -> `routing`
- `agent.dispatch` -> `delegating`
- `mailbox.sent` -> `queued`
- `mailbox.waiting` -> `waiting`
- `mailbox.received` -> `processing`
- `agent.error` / `mailbox.error` -> `error`

`Progress` の job 詳細では少なくとも以下を確認できる。

- 現在 phase
- owner
- status
- latest chat report
- latest worker note
- latest coder note
- failure kind
- failure reason
- recent events

## 5. System で見える内部イベント

現行 `System` は少なくとも以下を表示対象にする。

- `routing.decision`
- `entry.stage`
- `tts.audio_chunk`
- `agent.dispatch`
- `mailbox.sent`
- `mailbox.waiting`
- `mailbox.received`
- `mailbox.error`
- `agent.error`
- 非ユーザー向け `agent.start`
- 非ユーザー向け `agent.note`
- 非ユーザー向け `agent.response`

これにより、`mio -> shiro -> coder -> shiro -> mio` の handoff を画面上で追える。

## 6. JSON ログ保持

永続ログの正本ファイル:

- 操作ログ: `workspace/orchestrator_event_log.jsonl`
- GC 監査ログ: `workspace/orchestrator_event_gc.jsonl`

永続ログは JSONL の append-only で保持する。後追い解析の正本は live event ではなく persisted log とする。

最低限の追跡項目:

- `timestamp`
- `type`
- `from`
- `to`
- `route`
- `job_id`
- `session_id`
- `channel`
- `chat_id`
- `content`

保持ポリシー:

- `retention_days: 14`
- `gc_interval_minutes: 60`

GC は TTL 外の行だけを temp file + rename で compaction し、結果を `orchestrator_event_gc.jsonl` に残す。

## 7. 主要 API

ライブ監視:

- `GET /viewer/events`
- `GET /audio-router/events`

外部確認 JSON:

- `GET /viewer/status`
- `GET /viewer/agents`
- `GET /viewer/agent/detail?id=...`
- `GET /viewer/jobs`
- `GET /viewer/job/detail?job_id=...`
- `GET /viewer/logs`
- `GET /viewer/audit/summary`

主な query:

- `scope=live|persisted`
- `type`
- `agent`
- `route`
- `job_id`
- `session_id`
- `chat_id`
- `limit`

## 8. 運用上の見方

重い依頼や失敗調査では、まず以下の順で見る。

1. `Ops`
2. `Progress`
3. `System`
4. `Jobs`

意味づけ:

- ユーザー向け報告の正本は `Timeline` 上の `mio -> user`
- 内部 handoff の正本は `System`
- job 単位の滞留確認は `Progress`
- 後追い監査の正本は persisted JSONL

## 9. 既知の制約

- `EventHub` は短期ライブ観測用であり、完全監査には使わない
- agent の `offline` 判定はフロント側の一定時間無更新に依存する
- `Progress` は event から導出した表示であり、厳密な workflow engine ではない
- 永続ログは JSONL であり、集計や長期分析は外部ツール利用を前提にする
