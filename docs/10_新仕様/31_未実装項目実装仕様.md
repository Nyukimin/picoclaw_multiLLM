## 1. 目的

本仕様は、`docs/10_新仕様/` に記載された現行仕様のうち、production code、runtime wiring、config、Viewer/API、E2E 確認まで揃っていない項目を洗い出し、段階的に実装できる粒度へ落とすための実装仕様である。

今回は実装そのものではなく、実装担当者が着手できるように、未実装 / 部分実装 / 要確認項目、重複仕様、対立仕様、実装 Phase、検証条件、docs 更新先を整理する。

実装仕様の通し番号は元仕様の番号に合わせない。ただし、各項目に参考仕様番号と参考文書を明記する。

### 5.2 Sandbox と Docker sandbox

#### 仕様A

- 文書: `29_Sandbox_Promotion_Gate仕様.md`
- 内容: Sandbox は worktree、temp dir、container などを含む隔離作業領域。

#### 仕様B

- 文書: `14_旧仕様未実装候補.md`
- 内容: 旧 OpenClaw 由来 Docker sandbox は移行対象外候補。

#### 対立点

Sandbox という語が、RenCrow の worktree / directory sandbox と旧 Docker sandbox 構想で混ざりやすい。

#### 優先判断

`29_Sandbox_Promotion_Gate仕様.md` を優先する。Docker は必須ではなく、MVP は worktree / sandbox root / Path Guard とする。

#### 実装仕様での扱い

Phase 9 では Docker を実装しない。`internal/infrastructure/security/sandbox_guard.go` の拡張と sandbox registry から始める。

### 5.3 自動実行と Human approval

#### 仕様A

- 文書: `22_Revenue_Operating_Principles仕様.md`, `23_Workstream_Operating_Loop仕様.md`
- 内容: Heartbeat や Revenue routine で継続的に確認、下書き、改善提案を行う。

#### 仕様B

- 文書: `24_Agent_Skill_Governance仕様.md`, `29_Sandbox_Promotion_Gate仕様.md`
- 内容: 外部送信、公開、販売、正式環境適用は Human approval 必須。

#### 対立点

継続作業ループが「勝手に投稿 / 送信 / 販売 / 適用」へ拡張される危険がある。

#### 優先判断

Human approval を優先する。

#### 実装仕様での扱い

Heartbeat / Revenue / Workstream は draft report までを自動化する。投稿、外部送信、課金、DB promoted、source code promotion は approval gate 必須。

#### Phase 11 実装メモ

2026-05-18 時点で、Heavy Worker route/provider switching のうち以下は着手済みである。

- `MessageOrchestrator` の `RouteANALYZE` は `HeavyAgent` が設定されている場合だけ Heavy 経路を実行する。
- `DistributedOrchestrator` の `RouteANALYZE` も `HeavyAgent` が設定されている場合だけ Heavy 経路を実行し、distributed event log に `heavy -> mio` の応答 evidence を残す。
- HeavyAgent 未設定時の `RouteANALYZE` は、Mio Chat へ fallback せず `no heavy agent available` として失敗扱いにする。
- runtime では `cmd/picoclaw/runtime_agents.go`, `cmd/picoclaw/runtime_orchestrator.go`, `cmd/picoclaw/runtime_distributed_mode.go` から HeavyAgent が local / distributed orchestrator へ注入される。
- ToolRunner result budget wrapper を追加し、`ai_workflow.context_budget_*` が設定されている場合は Chat / Worker の runtime RunnerV2 に接続する。
- ToolRunner result が warning 閾値に達した場合は response metadata に `context_budget_*` を付与し、stop 閾値に達した場合は大きな tool result を次の LLM tool-loop context に戻さず error response にする。
- runtime で AI Workflow store が有効な場合、ToolRunner result budget wrapper は `ai_context_usage` を自動保存し、warning / stop 閾値に達した場合は `context_budget_warning` / `context_budget_exceeded` event を同じ store へ保存する。
- runtime で AI Workflow store が有効な場合、primary LLM provider middleware も provider 呼び出し前の `ai_context_usage` を自動保存し、warning / stop 閾値に達した場合は `context_budget_warning` / `context_budget_exceeded` event を同じ store へ保存する。
- runtime で AI Workflow store が有効な場合、local / distributed の `RouteANALYZE` は Heavy 実行開始 / 完了 / 失敗を `heavy_worker_started` / `heavy_worker_completed` / `heavy_worker_failed` event として保存する。
- runtime で SuperAgent store が有効な場合、`RunController` を作成し、local / distributed orchestrator へ注入する。Lead Agent run の実行中 context は `run_id` ごとに登録され、pause API から cancellation を要求できる。
- `/viewer/superagent/runs/pause` / `resume` は `runtime_control_applied` と `runtime_control_action` を返す。pause は `cancel_requested`、resume は停止済み処理の再起動ではなく `resume_marker_cleared` として扱う。
- `RunQueueItem` と `run_queue` JSONL / SQLite persistence を追加し、`/viewer/superagent/run-queue` / `claim` / `complete` で queued item の作成、due item の claim、completed / failed / cancelled 記録を行える。
- Viewer Ops は SuperAgent summary で `run queue` / `queued` 件数を表示する。
- `run_queue_scheduler_enabled=true` の場合だけ opt-in scheduler を開始し、due item を claim して local / distributed orchestrator へ `superagent` channel の work item として渡し、completed / failed と trace event を保存する。
- scheduler は `resume` / `process_message` / `chat` action のみ実行し、外部送信、PR作成、正式環境変更は実行しない。
