# 新仕様 概要

## 目的

この文書は、RenCrow のリファクタリング後の構成を、新しい作業基準として読みやすく整理するための概要である。

Phase 1 から Phase 25 では、`cmd/picoclaw/main.go`、`MessageOrchestrator`、`CodeExecutor`、`DistributedOrchestrator` に集中していた責務を、route、response、session、event、TTS、code execution、distributed transport などの単位へ分割した。

この新仕様では、次の状態を目標構成として扱う。

- `cmd/picoclaw` は composition root として薄く保つ。
- Application 層は usecase と orchestration を担当する。
- Domain 層は契約、値、状態、責務境界を担当する。
- Infrastructure 層は provider、persistence、transport、tool、STT/TTS などの技術詳細を担当する。
- Adapter 層は Viewer、channel、health、config など外部入出力を担当する。

## 正本仕様との関係

実装判断で迷った場合の一次参照は、引き続き `docs/01_正本仕様/実装仕様.md` とする。

`docs/10_新仕様/` は、正本仕様に合わせて整理された現在の構成を説明する補助仕様である。正本仕様と矛盾する場合は、正本仕様を優先し、このフォルダの文書を更新対象として扱う。

## 最重要原則

### モジュール化

機能単位で責務を分ける。単にファイルを分けるだけではモジュール化とは扱わない。

各モジュールは、少なくとも次を説明できる状態にする。

- 入力
- 出力
- 副作用
- 永続化
- ログ
- エラー契約
- 差し替え時の影響範囲

### 仕様と実装箇所の対応

仕様変更時は、その仕様を実装する主担当ファイルまたは主担当パッケージを 1 対 1 に説明できる状態を保つ。

1 つの仕様変更が複数箇所へ無秩序に広がる場合は、次のどちらかが崩れていると判断する。

- 仕様の粒度が大きすぎる。
- モジュール分割または実装配置が悪い。

その場合は、先に仕様単位、interface、contract、DTO、event、adapter 境界を見直し、巨大な `service` / `manager` / `helper` / `util` へ吸収して解決しない。

### 疎結合

呼び出し側は内部実装ではなく、interface、contract、event、DTO、adapter に依存する。

ある機能を差し替えるとき、他の機能や別の層へ影響が広がらない構造を優先する。

### 共通化の制限

「便利だから共有する」「似ているからまとめる」だけの共通化は禁止する。

巨大な `service` / `manager` / `helper` / `util` を新設して、依存を集約するだけの整理は行わない。

## Chat / Worker / Coder 境界

### Chat

- ユーザー対話を受ける。
- ルーティング判断を行う。
- 結果を返す。
- 実行の詳細、ファイル操作、破壊的操作を抱え込まない。

### Worker

- 実行主体である。
- Coder が生成した plan / patch を実行する。
- file / shell / git / test 実行を担当する。
- policy、protected pattern、workspace 制約、実行ログを守る。

### Coder

- 設計、plan、patch、proposal 生成を担当する。
- 破壊的操作を直接実行しない。
- 実行責務を持たない。

## 観測と検証の原則

- テスト通過だけで完了扱いしない。
- Viewer や音声が関係する変更では、実ブラウザまたは同等の E2E で最低 1 session を追う。
- fallback は成功ではなく、失敗または回復経路として記録する。
- Viewer 表示、音声、口パク、ログは別々の契約として扱う。
- repo example、live runtime config、Viewer 表示値を混同しない。
