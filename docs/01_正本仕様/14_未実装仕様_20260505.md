## 2. P0: LLM接続

### 2.1 MLX OpenAI互換 provider 主経路

実装状況:

- `local_llm.enabled=true` の場合、Chat / Worker / Wild は local OpenAI互換 provider で生成される。
- `local_llm.enabled=true` の場合、Ollama設定なしでも config validation を通過できる。
- 既存Ollama運用は `local_llm.enabled=false` のまま維持する。

実装方針:

- MLX専用 provider は作らない。実装済み。
- 既存の OpenAI互換 provider を local base URL で使う。実装済み。
- provider種別は `local_openai`。実装済み。
- model名は `Chat` / `Worker` / `Wild` を送る。実装済み。

最小受け入れ条件:

- configだけで Chat / Worker を MLXサーバへ向けられる。
- Ollamaなしでも Chat / Worker が起動できる。
- Wild用途の呼び出し先を生成できる。

### 2.2 `Chat` / `Worker` / `Wild` alias routing

実装状況:

- `Chat` / `Worker` / `Wild` は `local_llm` config の model alias として実装済み。
- `mio` は Chat provider、`shiro` は Worker provider に接続済み。
- Wild provider は生成済み。汎用ルーティングの自動分岐は未実装。

実装方針:

| alias | 実装上の役割 | 用途 |
|---|---|---|
| `Chat` | `mio` の最終応答 provider | 会話、音声UI、自然なやり取り |
| `Worker` | `shiro` の実務 provider | 要約、整理、RAG、通常画像解析 |
| `Wild` | 創作用 provider | 物語、画像プロンプト、創作画像解析 |

最小受け入れ条件:

- ルーティングが `Wild` を選べる。未実装。
- 明示指定または用途判定で Wild provider を呼べる。未実装。
- Chat / Worker のエイリアスはユーザー向け名として安定する。

### 2.3 timeout / warmup / concurrency

実装状況:

- MLX初回ロードを想定した 120秒以上の timeoutを追加済み。
- 起動後 warmupを追加済み。
- global concurrency と model別 concurrency queue を追加済み。

実装方針:

| 項目 | 初期値 |
|---|---|
| request timeout | 120秒以上 |
| global concurrency | 2 |
| per model concurrency | 1 |
| warmup | `Chat`, `Worker`, `Wild` へ `max_tokens: 1` |
| 優先度 | Chat > Worker > Wild |

最小受け入れ条件:

- 6エージェント利用時も同一MLXサーバへ無制限並列送信しない。
- Chat応答がWorker/Wildの長い処理で詰まりにくい。

## 3. P1: 記憶OSの土台

### 3.1 SQLite hot store

実装状況:

- 会話L1/hot storeとして `L1SQLiteStore` を追加済み。
- `conversation.l1_sqlite_path` が設定されている場合、`Store()` 時に同じメッセージを SQLite にミラー保存する。
- 保存時は `conv:<thread_id>` namespace、`observed` state、`L1` layer を付与する。
- Redis active thread が取れない場合、L1 SQLite の直近会話イベントをRecall候補として返す。
- Search Cache はL1 SQLiteに部分実装済み。
- Event Log は `l1_event_log` として保存/取得APIまで部分実装済み。
- 会話保存、Search Cache保存、記憶状態更新はEvent Logへ自動記録する。
- Event LogのViewer表示と運用導線は未実装。

実装方針:

- Redisを即削除せず、SQLiteを新規標準hot storeにする。部分実装済み。
- Redisは optional backend として残す。継続中。
- L1用途を SQLite WAL で扱う。実装済み。

最小受け入れ条件:

- 今日の会話イベントをSQLiteへ保存できる。
- `thread_id`, `namespace`, `memory_state`, `created_at`, `updated_at` を持つ。
- アプリ再起動後も今日の記憶をRecall候補にできる。

### 3.2 L0/L1/L2/L3 統合

未実装:

- 現行の短期/中期/長期と最新仕様の L0/L1/L2/L3 が未統合。
- RecallPackの出力にレイヤー情報が十分に残らない。

実装方針:

| レイヤー | 実装 |
|---|---|
| L0 | Go runtime + rolling summary |
| L1 | SQLite WAL |
| L2 | DuckDB |
| L3 | DuckDB + Qdrant + Parquet |

最小受け入れ条件:

- RecallPackに各候補の `layer` が付く。
- 古い会話全文を毎回LLMへ再送しない。
- L0は直近数往復 + rolling summary に抑える。

### 3.3 namespace分離

未実装:

- `conv:<thread_id>`, `user:<uid>`, `char:<persona>`, `kb:<domain>` のbuilder/validatorは実装済み。
- L1保存・取得・Event Log入口ではnamespaceを検証する。
- `user:` / `char:` / `kb:` へconfirmedコピーするpromoterは実装済み。
- 明示UIまたはvalidatorからpromoterを呼ぶ連携は未実装。

実装方針:

| namespace | 用途 |
|---|---|
| `conv:<thread_id>` | 会話スレッド記憶 |
| `user:<uid>` | ユーザー記憶 |
| `char:<persona>` | キャラ/役割記憶 |
| `kb:<domain>` | 知識DB |

最小受け入れ条件:

- 保存時に namespace が必須。
- Recall時に namespace filter を使える。
- `user:<uid>` への確定保存は明示またはvalidator通過後だけ。

### 3.4 記憶昇格状態

部分実装:

- L1会話イベントは `observed` / `candidate` / `confirmed` を保存できる。
- `UpdateMemoryState` で状態を更新できる。
- `RecentByState` で候補・確定記憶を状態別に取り出せる。

未実装:

- 明示操作で `candidate` を確認・破棄・確定するUIがない。
- validator通過後に `confirmed` へ昇格する連携がない。
- 確定記憶を `user:<uid>` / `char:<persona>` / `kb:<domain>` へ昇格保存するUI/validator連携がない。

実装方針:

```text
observed
  -> candidate
  -> confirmed
```

最小受け入れ条件:

- 推測保存は `observed` または `candidate` にしか入らない。
- `confirmed` は明示操作か validator 通過が必要。
- Viewerで状態を確認できる。

## 4. P1: 外部取得と検証

### 4.1 Source Registry

部分実装:

- L1 SQLiteに `l1_source_registry` を追加済み。
- `source_id`, `url`, `kind`, `trust_score`, `fetch_interval`, `license_note`, `enabled` を保存できる。
- `SourceTrustScores()` でvalidatorへ渡すsource trust mapを取得できる。
- 保存時に `source_registry.saved` を Event Log へ記録する。

未実装:

- Source Registryからfetcher/schedulerへ定期取得対象を渡す連携。
- YAML import/export。
- UIまたはCLIでの登録・無効化導線。

実装方針:

- `source_registry.yaml` またはDB tableを作る。
- RSS / Atom / 公式API / GitHub / Hugging Face / PyPI / MediaWiki を登録対象にする。
- 検索APIは fallback として扱う。

最小受け入れ条件:

- sourceごとに `source_id`, `url`, `kind`, `trust_score`, `fetch_interval`, `license_note` を持つ。実装済み。
- 登録されていない定期取得を行わない。

### 4.2 staging schema

部分実装:

- L1 SQLiteに `l1_staging_item` を追加済み。
- `raw_text` と `summary_draft` は別fieldで保存する。
- `raw_hash`, `keywords`, `license_note`, `validation_status` を保存する。
- 保存時に `staging.item_saved` を Event Log へ記録する。
- JSONL export/importを実装済み。

未実装:

- DuckDB / Parquet へのstaging export/import。
- `confirmed` memoryへのpromoter連携は実装済み。
- Source Registryからの定期取得投入。

実装方針:

staging item に最低限入れる項目:

| field | 用途 |
|---|---|
| `event_id` | 取得単位ID |
| `source_id` | Source Registry参照 |
| `source_url` | 出典URL |
| `fetched_at` | 取得日時 |
| `published_at` | 公開日時 |
| `raw_text` | 外部取得本文 |
| `raw_hash` | 重複排除 |
| `summary_draft` | LLM要約案 |
| `keywords` | 検索・分類用 |
| `license_note` | 利用条件 |
| `validation_status` | 検証状態 |

最小受け入れ条件:

- official DB へ入れる前に staging に保存される。SQLite入口は実装済み。
- raw と summary が別fieldで保持される。実装済み。

### 4.3 validator / promoter

部分実装:

- `ValidateStagingItem()` で L1 staging item を検証できる。
- 通過時は `validated`、失敗時は `rejected` に更新する。
- 検証結果は `staging.item_validated` として Event Log に残す。
- 現時点の検証項目は、URL妥当性、raw_hash重複、日付妥当性、source trust、license note、memory type、sensitive marker。
- `PromoteValidatedStagingItemToMemory()` で、validated済みstagingだけを `user:` / `char:` / `kb:` 等の `confirmed` memoryへ昇格できる。
- `PromoteValidatedStagingItemToNews()` で、validated済み外部取得stagingだけを News DBへ昇格できる。
- 昇格結果は `memory.promoted_from_staging` として Event Log に残す。

未実装:

- Source Registryのtrust scoreと連動した自動検証。
- DuckDB/Qdrant Knowledge DB 本体へのpromoter。
- 検索結果や外部取得結果を各official storeへ入れるための型別promoter。

実装方針:

validatorで見る項目:

- schema妥当性
- URL妥当性
- hash重複
- 日付妥当性
- source trust
- sensitivity
- license note
- memory type

最小受け入れ条件:

- validator失敗データは official store に入らない。L1 staging itemのrejected化は実装済み。
- promoterは validator通過済みだけを昇格する。`confirmed` memory / News DBへの昇格では実装済み。
- Codex/Coworkは staging まで。本番DB直接writeは禁止。

## 5. P2: Recall / RAG / News

### 5.1 Search Cache

部分実装:

- L1 SQLiteにSearch Cacheを持つ。
- query正規化、hash、retrieved_at、expires_at、source_urlを管理する。
- TTL内の同一queryはfresh hitとして取得できる。
- fresh hitはRecall Packの `SearchCacheSnippets` に出典付きで入る。
- MioのWeb検索はcache-firstで動き、miss時の検索結果をL1 Search Cacheへ保存する。
- ToolRunnerの `web_search` はV1/V2ともcache hookを参照でき、main起動時にConversation L1へ配線する。

未実装:

- 類似query抑制は未実装。
- Event Log / Search CacheのViewer表示は未実装。

実装方針:

- 検索前に `GetFreshSearchCache` を確認し、hitした場合は外部検索を省略する。
- miss時だけ外部検索し、結果を `SaveSearchCache` に保存する。

最小受け入れ条件:

- 同一queryの短時間再検索を避ける。
- cache hitもRecall Packに出典付きで入れられる。

### 5.2 News DB / Daily Digest

部分実装:

- L1 SQLiteに `l1_news_item` を追加済み。
- validated済みの `external_fetch` / `search_result` staging itemだけをNews DBへ昇格できる。
- `raw_text`, `summary_draft`, `source_id`, `source_url`, `published_at`, `raw_hash`, `keywords`, `license_note` を分離保存する。
- category別に `RecentNewsItems()` で取得できる。
- L1 SQLiteに `l1_daily_digest` を追加済み。
- `BuildDailyDigest()` で日付・category別にNews DBから決定的digestを作成できる。
- `RecentDailyDigests()` でdigestを取得できる。

未実装:

- 朝昼夜スロットのdigest生成。
- LLMによるdigest再要約。
- DigestのViewer表示。
- DuckDB / Parquet archive連携がない。
- RSS fetcherからSource Registry経由で自動投入する連携がない。

実装方針:

- RSS/API -> staging -> validator -> News DB。
- raw_text / summary_draft / keywords / source metadata を分離する。
- 朝昼夜または日次のdigestを作る。

最小受け入れ条件:

- 今日のニュース候補を一覧できる。L1 News DBでは実装済み。
- 雑談時に News DB とユーザー記憶を合わせてRecallできる。

### 5.3 Knowledge DB 汎用domain

部分実装:

- L1 SQLiteに `l1_knowledge_item` を追加済み。
- validated済みstaging itemを `kb:<domain>` の汎用knowledge itemへ昇格できる。
- `title`, `domain`, `raw_text`, `summary_draft`, `source_id`, `source_url`, `raw_hash`, `keywords`, `license_note` を分離保存する。
- domain別に `RecentKnowledgeItems()` で取得できる。

未実装:

- DuckDB FTS / Qdrantとの自動同期。
- 共通コアschemaのDuckDB/Parquet archive化。
- 映画・小説・音楽などの初期投入pipeline。

実装方針:

- 共通コア schema を作る。
- DuckDB FTS / Qdrant を組み合わせる。
- 最初は小さいdomainから始める。

最小受け入れ条件:

- `kb:<domain>` で保存・検索できる。L1保存と一覧取得は実装済み。
- 固有名詞検索と意味検索を併用できる。

### 5.4 RecallPack token予算制御

部分実装:

- `PromptConstraints.RecallBudgetRatio` を追加済み。
- `DefaultConstraints()` は `RecallBudgetRatio=0.10` を返す。
- `RecallPack.ApplyRecallBudget()` で中期要約、長期事実、KB、検索キャッシュ候補をcontext長比率でtrimできる。
- ConversationEngineはRecallPack返却前に予算制御を適用する。

未実装:

- 精密tokenizerとの連携。
- role-filtered retrievalとの統合。

実装方針:

- context長の約1割をRecall Pack目安にする。
- Chat / Worker / Wild のモデルごとに上限を分ける。

最小受け入れ条件:

- 長い記憶が増えても prompt が肥大化しない。概算tokenでは実装済み。
- どの候補を落としたかログに残る。
