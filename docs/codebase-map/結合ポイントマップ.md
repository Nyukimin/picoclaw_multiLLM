## データフロー

```text
External input
  ├─ LINE/Slack/Discord/Telegram/Viewer
  ↓
Adapter handler
  ↓
MessageOrchestrator
  ├─ Mio route decision
  ├─ Chat response
  ├─ Worker/Shiro execution
  ├─ Coder proposal -> WorkerExecutionService
  ├─ events/report/session
  └─ TTS/VTuber/Idle notifier
  ↓
Adapter response / Viewer event
```

```text
Source Registry / memory flow
  ├─ Viewer or CLI saves source
  ├─ sourcefetcher sweeps due sources
  ├─ L1SQLiteStore stages item
  ├─ validator marks pending/validated/rejected
  └─ validated item promotes to memory/news/knowledge
```

## 優先度の高いチェーン

1. Chat/Worker/Coder route chain: `MioAgent.DecideAction` -> `MessageOrchestrator` -> route-specific agent -> response/report.
2. Code execution chain: Coder proposal -> PatchCommand -> WorkerExecutionService -> protected checks -> execution result.
3. Viewer observation chain: Application event -> EventHub/SSE -> JS tab rendering -> event log/history.
4. Memory chain: Conversation manager -> L1 store -> memory state/staging/promote -> Viewer memory panels.
5. LLM ops chain: runtime config -> provider factory -> health/status handlers -> Viewer LLM ops.

## 落とし穴

- `config` の値が repo example、runtime local、Viewer表示で三重化しやすい。
- Worker 実行系は `PatchCommand`、`WorkerExecutionService`、`ToolRunner`、`PolicyEngine` の複数層で安全判断する。
- Viewer不具合は Go handler と JS/CSS の両方を確認する必要がある。
- Source Registry は保存、stage、validate、promote が別フェーズで、直接正式記憶化しない。
