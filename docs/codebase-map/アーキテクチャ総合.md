# アーキテクチャ総合

## 概要

RenCrow は Go の Clean Architecture 風構成を持ち、外部入口を Adapter、調整を Application、契約を Domain、技術実装を Infrastructure に分けている。  
実運用では `cmd/picoclaw/main.go` の wiring、`MessageOrchestrator` の route dispatch、Viewer/SSE 観測、L1 memory/source registry の状態遷移が変更影響の中心になる。

## 全体構造

```text
cmd/picoclaw
  └─ runtime wiring / CLI / HTTP server

internal/adapter
  └─ LINE, Viewer, health, config, channels, chrome bridge

internal/application
  └─ orchestrator, worker execution, idlechat, execution, sourcefetcher, tts, health

internal/domain
  └─ agent, routing, patch, tool, conversation, memory, session, execution

internal/infrastructure
  └─ llm, tools, security, persistence, transport, stt, tts, vtuber, mcp
```

## 主要データフロー

### Chat/Worker/Coder

```text
channel/viewer input
  -> adapter handler
  -> MessageOrchestrator.ProcessMessage
  -> Mio route decision
  -> route-specific agent or Worker/Coder path
  -> report/event/session/TTS hooks
  -> response to adapter + Viewer event stream
```

### Code execution

```text
Coder proposal
  -> domain proposal / patch command
  -> WorkerExecutionService
  -> protected pattern and command checks
  -> file/shell/git execution
  -> report store / event emission
```

### Memory/Source Registry

```text
Source save or conversation event
  -> L1SQLiteStore
  -> observed/candidate/staging state
  -> validation
  -> promotion to memory/news/knowledge
  -> Viewer memory/source panels
```

## Phase 2 で発見した知見

- `cmd/picoclaw/main.go` は多機能な composition root であり、単一機能の変更でも wiring 変更が必要になる可能性が高い。
- `L1SQLiteStore` は memory/source registry/staging/news/knowledge/search cache を横断するため、状態遷移をまたぐ修正は小さく分けるべき。
- Viewer は単なる静的UIではなく、SSEと実行ログを通じた観測面なので、コードテストだけでは品質判定が不足する。
- `WorkerExecutionService` と `ToolRunner` の安全境界は重複して見えるが、実行主体と tool 実行要求で文脈が異なる。
