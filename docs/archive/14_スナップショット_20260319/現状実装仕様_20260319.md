## 3. IdleChat 現況仕様

### 3.1 モード一覧

| モード | 開始方法 | 説明 |
|---|---|---|
| `manual` | `/viewer/idlechat/start` | 通常 IdleChat を即時開始可能な待機状態にする |
| `idle` | 自動起動 or manual 経由 | 通常雑談セッション |
| `forecast` | `/viewer/idlechat/forecast` | 未来展望セッション |
| `story` | `/viewer/idlechat/story` | 物語再構成セッション |

内部状態としては `manualMode`, `chatActive`, `sessionMode`, `currentTopic` を保持する。

### 3.2 起動条件

- 参加者は 2 名以上必須
- `chatBusy` または `workerBusy` の間は自動起動しない
- `manualMode=false` の場合、`interval_min` を超えるアイドル時間が必要
- `nextTopicAt` が未来時刻なら待機

### 3.3 自動ローテーション

自動起動時は以下の順でセッション計画を回す。

1. `single`
2. `double`
3. `external`
4. `forecast` の各ドメイン

通常系を 3 回行った後に、未来展望 1 回を挟む構成である。

### 3.4 中断条件

以下が発生すると IdleChat は停止または中断される。

- ユーザー activity
- Chat 側 busy
- Worker 側 busy
- 手動停止

中断時は `chatActive=false`, `sessionMode=""`, `currentTopic=""`, `sessionContext=""` に戻す。

## 4. Story Mode 現況仕様

### 4.1 位置づけ

Story Mode は `forecast` と並ぶ専用セッションであり、Viewer の「物語」ボタンから開始する。
通常の対話ターンではなく、Mio が物語を連続朗読する構成を取る。

### 4.2 データソース

- 物語データは `idle_chat.story_data_dir` から読み込む
- 現在の既定データは `data/story/*.json`
- 2026-03-19 時点で JSON ファイルは `27` 件存在する

各 JSON は以下を内包する。

- `StorySource`
- `StorySpec`
- `StorySkeleton`
- style 別 twist 情報

### 4.3 実行フロー

Story Mode は概ね以下で動作する。

1. `StartStoryMode()` で `chatActive=true`, `sessionMode="story"`
2. rewrite style を履歴から選定
3. ソース物語を選択
4. 決定論的な `prepareStory()` で分析・骨格化・改変計画を構築
5. LLM で draft 生成
6. 必要なら revision を試行
7. 失敗時は deterministic fallback または source retelling fallback を使用
8. Mio が導入、改題、本編、締めを chunk 単位で発話
9. `SessionSummary` と transcript を保存

### 4.4 リトライとフォールバック

- draft: 最大 3 回
- revision: 最大 3 回
- source 切替: 最大 3 作品

すべて失敗した場合は Story Mode を継続せず、通常 `idle` セッションへフォールバックする。

### 4.5 出力形式

Story Mode の発話はすべて `idlechat.message` として Timeline に流れる。
メッセージ本体は `MessageTypeIdleChat` で `CentralMemory` にも記録される。

チャンク長の目安:

- 最大 `90` runes
- 最小 `28` runes

### 4.6 履歴保存

Story Mode の `SessionSummary` には通常項目に加えて以下を保存する。

- `source_title`
- `rewrite_style`
- `story_title`
- `story_text`
- `story_draft_text`
- `story_revision_note`
- `story_ending_flavor`

`strategy` は `story:{rewrite_style}` 形式になる。

## 5. Viewer / IdleChat API 現況仕様

### 5.1 REST API

| エンドポイント | メソッド | 用途 |
|---|---|---|
| `/viewer/idlechat/start` | `POST` | manual mode 開始 |
| `/viewer/idlechat/forecast` | `POST` | forecast session 開始 |
| `/viewer/idlechat/story` | `POST` | story session 開始 |
| `/viewer/idlechat/stop` | `POST` | idlechat 停止 |
| `/viewer/idlechat/status` | `GET` | 現在状態取得 |
| `/viewer/idlechat/logs` | `GET` | 履歴取得 |

### 5.2 API レスポンスの基本形

状態系 API は以下の情報を返す。

- `ok`
- `mode`
- `manual_mode`
- `chat_active`
- `current_topic`

`/viewer/idlechat/logs` では追加で `history` を返す。

### 5.3 Viewer UI

Viewer の入力バーには以下の IdleChat 操作が実装されている。

- `通常Chat`
- `未来展望`
- `物語`
- `IdleChat開始`
- `IdleChat停止`

UI 上の状態表示は mode ごとに変化する。

- 通常: `IdleChat: off/on/talking`
- 未来展望: `Forecast: ready/talking`
- 物語: `Story: ready/talking`

### 5.4 履歴表示

Viewer の IdleChat パネルは `history` を newest-first で表示する。
各行は展開可能で、保存済み transcript を copy できる。

## 6. VTuber / VTS 現況仕様

### 6.1 実装状態

VTuber 連携は Draft 仕様ではなく、最小実装がすでにコードに存在する。

- `buildVTuberBridge()` で character 設定を読み込む
- `internal/infrastructure/vtuber/client_bridge.go` が WebSocket 接続を管理する
- `VTuberBridge.PublishEmotion()` で character ごとに `emotion_tick` を送信する

### 6.2 設定要件

`vtuber.enabled=true` の場合、各 character に以下が必須。

- `audio_output`
- `vts_host`
- `vts_port`
- `expression_map`

全体設定の制約:

- `tick_interval_ms`: `50` から `100`
- `connect_timeout`, `write_timeout` はミリ秒設定

### 6.3 送信 payload

VTS へ送る論理イベントは `emotion_tick` であり、payload には以下を含む。

- `speaking`
- `valence`
- `arousal`
- `intensity`
- `emotion_label`
- `expression` 任意
- `audio_output` 任意

### 6.4 感情ラベル

現実装では TTS の EmotionState から以下の代表ラベルへ写像する。

- `happy`
- `surprised`
- `annoyed`
- `thinking`
- `calm`
- `neutral`

## 7. Audio Router 現況仕様

### 7.1 目的

Coder4 側でキャラクター別音声出力先を扱うため、Audio Router 用設定と SSE 出口がある。

### 7.2 設定要件

`audio_router.enabled=true` の場合、以下が必須。

- `sse_url`
- `device_map`
- 各 device の `device_id`

制約:

- `connect_timeout_ms >= 1000`
- `download_timeout_ms >= 1000`
- `retry_delay_ms >= 250`
- `buffer_ms = 20..5000`

### 7.3 イベント導線

- HTTP endpoint: `/audio-router/events`
- Viewer EventHub の `tts.audio_chunk` から Audio Router 向け payload を抽出して配信する

## 8. 分散実行まわりの現況

### 8.1 Local Worker / Coder 応答

Local worker / local coder の応答は `domain/transport.Message` で返し、`result` payload を保持できる。

### 8.2 ResultPayload の拡張

現時点の `ResultPayload` は以下の失敗分類メタデータを含む。

- `failure_kind`
- `failure_reason`
- `retryable`
- `failed_index`

このため、単に成功/失敗だけでなく、再試行可否と最初の失敗位置まで呼び出し元へ返せる。
