# 詳細実装仕様 02: チャネル網羅不足

**更新日**: 2026-03-19  
**ステータス**: 現行実装ベース  
**親仕様**: `docs/実装仕様_OpenClaw移植_v1.md`

---

## 1. 概要

RenCrow のチャネル層は、すでに LINE / Telegram / Discord / Slack / Viewer(local) の複数入口を持っている。  
したがって現状の課題は「3チャネル未実装」ではなく、各チャネルの実装深度と共通化の到達点を明確にすることである。

現行実装で共通化されている要素:

1. `ChannelEvent` による受信イベント正規化
2. `BuildSessionID()` による session 規約
3. `Registry` による有効チャネル管理
4. `channels list|probe` CLI による疎通確認

---

## 2. 共通契約

### 2.1 ChannelEvent

**ファイル**: `internal/adapter/channels/types.go`

```go
type ChannelEvent struct {
    Channel   string
    ChatID    string
    UserID    string
    MessageID string
    Text      string
    Timestamp time.Time
    Raw       []byte
}
```

用途:

- LINE / Telegram / Discord / Slack の入力差分を吸収
- orchestrator へ渡す前の最小共通表現
- `Raw` はデバッグ・追跡用

### 2.2 Adapter 契約

現行の最小 I/F は次の通り。

```go
type Adapter interface {
    Name() string
    Send(ctx context.Context, chatID, text string) error
    Probe(ctx context.Context) error
}
```

旧草案にあった `Start/Stop/Verify` を共通 I/F に強制する形ではない。  
Webhook 検証や HTTP 処理は各 adapter が独自に `http.Handler` として持つ。

### 2.3 Session 規約

**ファイル**: `internal/application/channel/normalize_service.go`

```go
func BuildSessionID(now time.Time, channel, chatID string) string
```

現行形式:

- `YYYYMMDD-{channel}-{chatID}`

加えて `NormalizeEntryPlatformChannel(platform, channel)` が unified entry の platform/channel を正規化する。

## 3. 現行チャネル実装

### 3.1 LINE

**ファイル**: `internal/adapter/line/handler.go`

- `/webhook`
- HMAC-SHA256 署名検証
- Webhook event を `ChannelEvent` に正規化
- session ID は `BuildSessionID(..., "line", userID)`

### 3.2 Telegram

**ファイル**: `internal/adapter/channels/telegram/adapter.go`

- `/webhook/telegram`
- `X-Telegram-Bot-Api-Secret-Token` 検証
- `sendMessage` による outbound
- `getMe` による probe
- session ID は `BuildSessionID(..., "telegram", chatID)`

### 3.3 Discord

**ファイル**: `internal/adapter/channels/discord/adapter.go`

- `/webhook/discord`
- 2 種類の入力を処理
  - relay payload
  - Discord interactions payload
- outbound は `POST /channels/{id}/messages`
- probe 実装あり
- session ID は `BuildSessionID(..., "discord", chatID)`

### 3.4 Slack

**ファイル**: `internal/adapter/channels/slack/adapter.go`

- `/webhook/slack`
- Slack Events API webhook を処理
- outbound は `chat.postMessage`
- `auth.test` による probe
- session ID は `BuildSessionID(..., "slack", chatID)`

### 3.5 Viewer / Local

- Viewer の `/viewer/send`
- Chrome bridge
- unified entry handler

これらは `viewer` / `local` チャネルとして session 化される。  
OpenClaw 的には GUI / local entry もチャネル面に含めて扱っている。

## 4. Registry と CLI

### 4.1 Registry

**ファイル**: `internal/adapter/channels/types.go`

`Registry` は有効アダプタの登録・一覧・一括 probe を担う。

主要メソッド:

- `Register(adapter)`
- `Get(name)`
- `List()`
- `ProbeAll(ctx)`

### 4.2 起動時配線

**ファイル**: `cmd/picoclaw/main.go`

`buildChannelRegistry(cfg)` で設定に応じて次を登録する。

- `telegram`
- `discord`
- `slack`

各 webhook handler も同様に条件付きで配線される。

- `/webhook/telegram`
- `/webhook/discord`
- `/webhook/slack`

### 4.3 CLI

`picoclaw channels` に以下がある。

- `channels list`
- `channels probe`

これにより、OpenClaw の channel status 導線に近い最小運用面は実装済みである。

---

## 5. OpenClaw 観点での差分

現行到達点:

- 複数チャネルの受信入口を持つ
- outbound send を各 adapter が持つ
- probe を共通 registry から叩ける
- session ID 規約はチャネル横断で統一されている

未到達 / 制約:

1. `ChannelAdapter` の完全統一 I/F はない
2. 認証検証ロジックは adapter ごとに個別実装
3. Gateway 1 箇所ですべてのチャネル契約を抽象化する層は薄い
4. 再送・重複イベント抑止の共通基盤は明示的にはない
5. WhatsApp / iMessage 等は未実装

---

## 6. 確認観点

- `cmd/picoclaw/main.go` で各 webhook が条件付き配線される
- `ChannelEvent` 正規化が Telegram / Discord / Slack で行われている
- `BuildSessionID()` が全チャネルで共通利用される
- `picoclaw channels list|probe` が使える

以上をもって、チャネル層は「未実装」ではなく、主要 4 系統の入力を持つ現行実装として扱う。今後の課題は網羅性そのものより、統一度と運用抽象化の引き上げである。
